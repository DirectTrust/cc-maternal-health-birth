# TX2: send-admission-notification

**REUSABLE TRANSACTION DEFINITION**

## Transaction Overview — WHY

Timely awareness of patient registration and admission events helps healthcare organizations coordinate services, maintain continuity of care, and respond to changes in a patient’s care setting. send-admission-notification provides a standardized way to communicate these events to other authorized participants in the patient’s care. By combining an immediately understandable notification with machine-processable event information, the transaction supports both human awareness and automated workflows, reduces dependence on manual notification processes, and helps relevant information reach the right participants when it is needed.

### Purpose and Scope

The purpose of send-admission-notification is to communicate a patient registration or admission event to an intended Information Recipient so that the recipient can recognize the event and incorporate the information into its supported workflow. The transaction conveys an HL7 Version 2 admission-related notification together with a corresponding human-readable healthcare communication. It establishes a reusable exchange pattern independent of the clinical program or organizational relationship in which it is used; a particular use case may impose additional patient identity, Context, or downstream activity requirements without changing the transaction’s fundamental purpose.

The transaction supports the following admission-related events:

- patient registration;
- hospital admission; and
- emergency department admission.

A Newborn Birth Admission A01 is processed as an admission notification for the newborn under TX2. For this maternal-health use case, it SHALL carry the mother’s established Perinatal Context Instance identifier and sufficient maternal-association information to support the separately identified TX3 send-birth-notification activity. Sections 2.2.2 and 7 define this prerequisite and the separation of processing outcomes.

The Payload and Payload Metadata may be represented using XD or FHIR packaging as supported by the receiving endpoint. The representation changes how the same Payload Metadata is encoded; it does not create a different transaction.

### Transaction Identity

The canonical transaction code is send-admission-notification. TX2 is a local editorial label assigned by the cc-maternal-health-birth Use Case Guide for readability and navigation; it is not the interoperable transaction identifier. The canonical transaction code is intended to remain stable and reusable across use cases.

### Framework Relationship

Framework relationship. This Transaction Definition specializes the common Transaction Framework defined in Chapter 3, including the terminology bindings in Section 3.7.7. Common transport, Workflow Activity Task, Workflow Status, patient identity, Context/correlation, Provenance, and message-metadata requirements apply unless this definition states a TX2-specific requirement. TX3 send-birth-notification defines the separate maternal document activity that may follow a newborn Birth Admission A01.

Clinical Content Author/Source, Workflow Requester / Information Source (Task.requester), SubmissionSet Source (SubmissionSet.sourceId), Transaction Sender, and Information Recipient are distinct roles. A single organization MAY fill several roles. Implementations SHALL preserve the distinction when different parties perform them.

## Message and Payload Requirements — WHAT

The following provisions describe message and payload requirements.

### Payload Packaging Structure

The TX2 Payload SHALL include the machine-processable HL7 Version 2 admission-related notification and a human-readable healthcare communication conveying the essential notification information. The human-readable communication MAY also be supplied as HTML.

The Structured Payload Package SHALL contain exactly one primary HL7 Version 2 notification, zero or one Workflow Activity Task, identical copies of the required human-readable text/plain communication and every supplied text/html alternative, and optional Provenance describing the included objects or activity. Secondary clinical documents and other supplemental Payload objects SHALL NOT be included. Clinical documents SHALL be sent separately using TX5 send-documents. FHIR resources needed solely to represent metadata and referenced actors or patient information are supporting resources, not additional submitted Payload objects.

Apply the common MIME packaging and human-readable content preservation requirements in Chapter 3 Section 3.8.4. The following tables identify the message-level components and the information objects required for TX2. Detailed common transport and ZIP MIME requirements are governed by Chapter 3.

Apply Chapter 3 Sections 3.7.5–3.7.6 and Appendix D for package completeness. All required payload and supporting references SHALL resolve within the transmitted Structured Payload Package. Review reports and inspection views outside that package do not supply required transmitted resources. Supporting patient, actor and endpoint resources do not acquire additional DocumentEntries merely because they support a reference.

When a Task is included in XD packaging, its supporting resources SHALL be contained in the Task with local fragment references. Provenance assertions and their agents SHALL reside in their own Provenance Collection Bundle. Do not reference another object’s contained resources or use nested containment. For FHIR metadata, Task support remains in the outer Collection Bundle; Provenance bundle entries remain inside their carrying bundle. Apply Chapter 3 and Appendix D for carried targets, security labels, and serialization.

Task absence does not change the transaction identity, admission-event requirements, or mandatory maternal Context requirements. TX2 support does not imply TX8 support.

#### Workflow Activity Identification

An intermediary updating package membership or Provenance SHALL preserve SubmissionSet.uniqueId/List business identifier. When a Workflow Activity Task is present, it SHALL also preserve its aligned Task.identifier and any applicable Workflow Status Update Endpoints. Updated representations receive new entryUUID/List.id values and, when present, Task.id values; update membership and affected references. These updates do not create a new logical transaction instance.

SubmissionSet.uniqueId identifies the logical TX2 transaction independently of Task presence. SubmissionSet.purpose SHALL identify send-admission-notification using DTCodeSystem. When Task is present, its designated Task.identifier SHALL align with SubmissionSet.uniqueId and Task.code SHALL match SubmissionSet.purpose in code and code system. The specific admission event classification SHALL NOT replace the transaction code.

#### Context Instance Association

TX2 SHALL apply the common Context and correlation rules defined by Chapter 3. Applicable established Context Instance identifiers SHOULD be carried in the Payload Metadata when known and authorized for the exchange. For the maternal-health use case, an admission-related notification may be associated with the patient’s established Perinatal Context Instance and applicable Visit Context Instance.

A newborn Birth Admission A01 SHALL carry the mother’s established Perinatal Context Instance identifier, including its assigning authority or namespace, as a related maternal Context identifier. Its type SHALL be urn:dt-org:dsm:map:2025:perinatal from the Chapter 3 DT Context Type ValueSet. The newborn remains the notification patient and, when Task is present, its Task.for subject; carrying the maternal Context identifier SHALL NOT assert that the newborn is the patient of the mother’s Perinatal episode. Distinguish maternal and newborn identifiers and Context associations in the source notification and package metadata, and in the Task when present.

The hospital is assumed to have previously received the mother’s established Perinatal Context Instance identifier through the birth-registration workflow or a shared Antepartum Summary document. It SHALL retain the maternal association and carry that identifier forward into the newborn Birth Admission A01 and applicable TX2 Context metadata, and into the Task representation when one is present. This is a use-case content requirement; do not assume that every base HL7 V2 A01 supplies it without an agreed implementation mapping. Do not generate a replacement episode identifier, substitute the newborn’s encounter identifier, or silently relabel a Pregnancy Context identifier as Perinatal. Resolve any relationship to the established Perinatal Context through authoritative context information.

The notification SHALL preserve source-supported mother–newborn association information and maternal identifiers with their assigning authorities. PID-21, Mother’s Identifier, is used when present in the selected HL7 V2 implementation; corroborating NK1 or other agreed source data MAY assist resolution but SHALL NOT replace the required established Perinatal identifier. The exact HL7 V2 field/extension mapping SHALL be established by the source implementation and preserved through transformation. The identifier does not encode a Direct address; authorized resolution of the maternal Context to the OB/practice and its preferred Direct endpoint is part of TX3 processing.

HL7 V2 source mapping and status. Distinguish the visit/encounter identifier in PV1-19 from an established episode identifier. HL7 V2.8 defines PV1-54 Service Episode Identifier and PV1-53 Service Episode Description; those fields are absent from the V2.5.1 base used by the current samples. PV1-54 is a candidate for the message patient’s service episode, not an adopted mapping for the related mother’s Perinatal Context in a newborn A01. No PV2 field is selected by this definition as a generic Context Instance identifier.

Illustrative provisional mapping. An illustrative provisional V2.5.1 mapping carries PERICTXID in an OBX with value type EI: OBX-5.1 is the identifier value, OBX-5.2 the namespace label, OBX-5.3 the universal assigning-authority identifier, and OBX-5.4 the universal identifier type. A separate PERICTXTYPE OBX with value type CWE carries the Context type code in OBX-5.1, its display in OBX-5.2 and its source coding-system designation in OBX-5.3. These locally named observations are provisional illustrative mappings; their use is not a claim that base HL7 defines these observation identifiers. Preserve the source coding-system designation and separately identify the established DTContextTypeCodeCS binding; do not silently replace a source L designation.

Source implementation mapping. The selected V2 version, source location, value type, assigning authority, Context type coding and subject association SHALL be documented by the implementation. A source rendering SHALL distinguish message-carried context from context supplied only by an optional Task, package metadata or an authorized lookup. It SHALL NOT make a missing source context appear to have been present in the original V2 message.

For a newborn Birth Admission, label the mother’s context “Related maternal Perinatal Context” and show the source-supported maternal identifier and namespace separately from the newborn’s patient identifier and PV1-19 visit identifier. State that the maternal context supports a separately identified TX3 activity; it does not make the newborn the patient of the maternal episode. PID-21 supports the maternal patient association but is not the Perinatal episode identifier. The provisional local OBX mapping, a later-version PV1-54 candidate and an actual agreed source profile SHALL remain distinguishable.

#### Transaction Correlation

The originating transaction concludes when the authorized Receiver Actor accepts or rejects the whole structured payload into its intended workflow. TX8 is a separate optional-capability transaction for reporting that disposition when Chapter 3 establishes an applicable reporting obligation. Only when a correlated TX8 report is expected shall the originating system apply the Chapter 3 reporting interval and, if none arrives, record outcome unconfirmed and requiring follow-up. Timeout does not establish rejection, acceptance, or non-receipt. A late report resolves the original outcome while preserving timeout and follow-up history.

The Content Consumer SHALL gather and maintain supplied Context Instance Identifiers with their values, assigning authorities, types, and subject associations. It SHALL preserve relevant identifiers in later exchanges concerning those contexts. Visit, perinatal, referral, order, request, and other contexts may continue beyond the individual transaction; a later exchange has its own transaction identity.

Apply the common Chapter 3 transaction correlation requirements. A responding TX8 SHALL identify the originating TX2 Transaction Instance and applicable Context Instance(s). Any subsequent maternal Birth Notification activity described in Section 7.2 establishes a separately identified activity and transaction.

When a Workflow Activity Task is present, it may carry applicable Workflow Status Update Endpoint(s), whole-payload acceptance reporting instructions, and correlation identifiers as defined in Chapter 3. Task absence does not by itself create or remove a TX8 obligation. Disposition-Notification-To remains a transport-level return address and SHALL NOT be interpreted as a Workflow Status Update Endpoint.

When TX8 reporting is applicable, determine its required destination and sending/receiving capabilities under Chapter 3. Preserve and accumulate any applicable endpoints carried in a Task. If Task is absent, the Chapter 3 MDN Direct-address fallback is available only when the Directory-discoverable CapabilityStatement declares TX8 supportsReceive=true; otherwise do not dispatch TX8, record the unsuccessful reporting obligation, and determine the originating TX2 outcome independently.

When a Task is present and applicable TX8 reporting instructions are established, the Content Creator MAY select an initial Workflow Status Update Endpoint from supplied discovery information or explicit configuration and SHALL carry the endpoint as required by Chapter 3. Subsequent actors preserve the applicable endpoint set. A receiver SHALL NOT be required to implement TX8 merely because it supports TX2.

TX2 uses the common Direct message metadata defined by Chapter 3. ## Transaction-Specific Processing — WHAT IS SPECIAL

A05 communicates advance registration/pre-admission and uses DT20260927-1 Hospital Registration Notification from DTTemporaryCodeCS. A04 arrival/check-in is outside this Use Case. Acceptance of A05 requires a patient match at the receiving site and acceptance of the notification into its supported registration workflow. Do not require a pre-existing clinical Visit merely because a future visit or admission is anticipated. A05 alone does not assert that the future clinical encounter has started.

Apply common Chapter 3 processing anomaly rules. When TX8 reporting is applicable, use Chapter 3 Section 3.9 and the TX8 send-workflow-status Transaction Definition; TX2 support alone does not imply TX8 sending or receiving support. The following qualifications are specific to TX2.

When a received transaction results in a defined terminal failure requiring TX8, apply the Extensible binding to MAPFailureReasonVS (http://objects.directtrust.org/standards/fhir/ValueSet/map-failure-reason) specified in Chapter 3 Section 3.9.2. Use a shared applicable code with an explanation; optional missing information does not alone establish rejection. Local filtering or preparation failures before this transaction is issued SHALL NOT be reported as rejection of a nonexistent transaction.

### Newborn Admission — Special Processing Path

A Newborn Admission does not change the processing requirements of the send-admission-notification transaction. The newborn admission notification is received, matched, validated, and processed as TX2 for the newborn patient, and any applicable terminal processing outcome reporting follows the conditional Chapter 3 TX8 rules.

Successful processing of a newborn Birth Admission A01 MAY trigger a separately identified TX3 send-birth-notification activity. TX3 uses the carried maternal association and established Perinatal Context to resolve the mother and her OB/practice endpoint and create a maternal Birth Notification CDA. The mother is the CDA recordTarget and the baby is the explicit subject of its newborn section. The generated maternal HTML Source Form uses verified source facts and resolved maternal Context. The original newborn A01 and its full rendering SHALL NOT be included as secondary objects in the outgoing maternal TX3 package; retain the source in the transforming system for traceability. TX3 has its own Transaction Instance, independently required Payload Metadata, actor roles and applicable Provenance; its Workflow Activity Task and TX8 reporting are governed by the TX3 and Chapter 3 requirements.

This separation is intentional: the Provenance of receiving and processing the newborn admission belongs to TX2; the Provenance of creating the maternal Birth Notification belongs to the subsequent creation activity; and the Provenance of transmitting and processing that Birth Notification belongs to the subsequent send transaction.

Failure of a separately initiated maternal Birth Notification creation or send activity SHALL NOT change an already established successful outcome for processing the newborn TX2. Determine and report each activity’s outcome independently according to its applicable transaction requirements.

### Patient and Context Resolution Qualifications

For A01 admission processing, an initially unknown patient does not by itself require rejection when the receiving endpoint’s declared policy permits establishing or resolving that patient. A05 advance-registration acceptance requires a match to an existing patient at the receiving site; new-chart establishment does not satisfy that requirement. If patient resolution under the applicable rule fails and prevents requested processing, determine TX2 rejection and apply TX8 reporting only when required under Chapter 3. No endpoint is required to establish a patient beyond its declared capabilities.

An absent optional Context identifier SHALL NOT, by itself, cause TX2 rejection. The maternal Perinatal identifier required for a newborn Birth Admission in this use case is not optional and remains required even when no Task is present. If it is missing, ambiguous, or unresolved, do not create or send an uncorrelated maternal Birth Notification. Determine whether the deficiency prevents mandatory TX2 processing: when it does, apply the originating TX2 disposition and any applicable Chapter 3 TX8 reporting; when newborn admission processing has succeeded and maternal notification generation is a separate downstream activity, preserve the successful TX2 outcome and record the downstream failure separately. Do not issue TX8 against a TX3 Transaction Instance that was never created. Do not assign the newborn as the patient of the mother's Perinatal Context.

## Relevant Examples — SHOW ME

These narrative patterns describe TX2 registration and admission scenarios. They are not references to supplied executable TX2 sample packages. XD and FHIR metadata options preserve the same transaction and event-classification semantics. For common whole-payload acceptance and structured payload rejection examples, see Section 8 of the TX8 send-workflow-status Transaction Definition.

### Maternal Hospital Registration

In the Mimi Shell reference scenario, the hospital registration notification is a TX2 send-admission-notification. SubmissionSet.purpose identifies send-admission-notification, as does Task.code when a Task is present. The principal HL7 V2 DocumentEntry uses classCode 86530-3 Hospital notification and typeCode DT20260927-1 Hospital Registration Notification. Patient identity and Patient Info follow the Chapter 3 rules, and applicable Perinatal/Visit Context identifiers are carried when known.

### Maternal Hospital Admission

For the hospital admission notification, the same TX2 Shared Activity is used. The principal HL7 V2 DocumentEntry uses classCode 86530-3 Hospital notification and typeCode 79429-7 Hospital admission notification. The transaction identity does not change merely because the event type changes.

### Newborn Admission

A newborn Birth Admission A01 is processed under TX2 for the newborn patient. It carries source-supported maternal-association information and the mother’s established Perinatal Context identifier, previously learned through the birth-registration workflow or Antepartum Summary sharing. The human-readable communication labels that Context as maternal. After successful TX2 processing, the receiving implementation may initiate TX3 send-birth-notification with a separate Transaction Instance and an optional Task under applicable TX3 requirements. TX3 creates the maternal CDA and generated HTML Source Form; it retains the original A01 for traceability without attaching it to the maternal package.

If newborn admission processing succeeds but the maternal Context or OB endpoint cannot be resolved for the separately requested downstream activity, the established TX2 success remains valid and TX3 generation is withheld. If mandatory TX2 processing is prevented by missing maternal information, determine TX2 structured payload rejection and apply conditional Chapter 3 TX8 reporting . These are different activity outcomes; neither case permits inventing maternal identifiers or an endpoint.
